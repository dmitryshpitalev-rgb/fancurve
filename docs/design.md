# FanCurve — дизайн

- **Дата:** 2026-09-16
- **Машина:** MacBook Pro 16" 2019 (A2141, `MacBookPro16,1`), i9-9980HK, Radeon Pro 5500M, T2, macOS 15.8 (Intel)
- **Инструменты:** Swift 6.1.2 из CommandLineTools (Xcode не установлен), SwiftPM, Swift Testing, Swift Charts
- **Статус:** дизайн согласован в диалоге; реализация начинается с проверки на железе (Фаза 0)

## 1. Зачем

macOS держит A2141 тихим ценой перегрева: сначала сбрасывает частоту процессора и только потом, когда уже жарко, раскручивает вентиляторы. CPU доходит до 95–100°C, корпус горячий, на кровати и на столе пользоваться неудобно.

FanCurve раскручивает вентиляторы раньше и сильнее по кривой, которую задаёт пользователь, — как в MSI Afterburner: одна кривая по самому горячему кристаллу (CPU или Radeon), обе вентилятора синхронно, — и заранее, по потребляемым ваттам.

## 2. Что входит и что нет

**Входит:**
1. Чтение температур CPU, GPU, корпуса и потребления CPU+GPU.
2. Кривая «горячий кристалл → обороты», как в MSI Afterburner, с графическим редактором: вход — более горячий из кристаллов CPU и Radeon, выход — один и тот же % диапазона для обоих вентиляторов.
3. Упреждение: кривая по усреднённым ваттам (включена по умолчанию) и кривая по корпусу (выключена по умолчанию); обе можно выключить.
4. Аварийка: при любом сбое управление возвращается macOS.
5. Автозапуск: демон стартует до входа в систему, менюбар — при входе.
6. История и графики за последний час.
7. Автографика: на зарядке всегда Radeon, на батарее автовыбор.

**Не входит (вырезано осознанно):** профили, автопереключение профилей, турбо-кнопка, CLI как основной интерфейс, поддержка других моделей Mac, возможность сделать тише, чем стоковый минимум оборотов.

### 4.2 Граница ядра

`FanCurveCore.Controller` — чистый автомат без IOKit и без часов. Демон кормит его событиями и исполняет его решения:

- **Вход тика:** `time` (монотонные секунды), сырые показания каналов (`cpu`, `gpu`, `chassis`, `power`, каждое `Double?`), `gpuActive: Bool`, фактические обороты вентиляторов.
- **События:** `startup(result)`, `setConfig`, `setEnabled`, `retry`, `willSleep`, `didWake`.
- **Выход тика:** режим и причина, сырые и отфильтрованные каналы, спрос по каждой кривой, ведущая кривая, итоговый %, целевые RPM, действие для актуатора: `none` / `apply([Int])` / `release` (отдельного `take` нет: демон включает принудительный режим вместе с каждой целью, так что захват — это первый `apply`).

Диапазоны вентиляторов (стоковый минимум и `F?Mx`) передаются контроллеру при создании. Запись в SMC, проверку записи и повтор при расхождении делает демон.

### 4.3 Язык

Язык: Swift 6.1. `FanCurveCore` и `FanCurveIPC` собираются в режиме языка Swift 6, остальной пакет — в режиме Swift 5 (меньше борьбы со строгой конкурентностью вокруг колбэков IOKit). Минимальная ОС — macOS 15.

Язык интерфейса (решение Димы от 29.09): русский, украинский или английский — по первому языку в списке предпочтений системы: русский → русский, украинский → украинский, любой другой → английский. Настройки в приложении нет. Все тексты лежат в `FanCurveUI/UIText.swift`, каждый в трёх вариантах; `UIText.language` решается при старте, `--snapshot DIR ru|uk|en` рисует экраны на заданном. Демон и `fancurvectl` говорят по-английски, как весь машинный слой: их сообщения приложение показывает как есть, а ошибки валидации кривых и сглаживания переводит само по их виду (`ValidationError.Kind`).

## 5. Контур управления

Цикл каждые 500 мс:

```
сенсоры → фильтры → кривые → max → правила безопасности → сглаживание → запись в SMC → проверка записи
```

### 5.1 Каналы

| Канал | Источник | Критичный | Ключи |
|---|---|---|---|
| `cpu` | max по ядрам и PECI | да | см. `docs/hardware-profile.json` (измеренный источник истины) |
| `gpu` | Radeon: SMC, запасной вариант — `ioreg Temperature(C)` | да | см. `docs/hardware-profile.json` |
| `chassis` | max по подлокотнику и днищу | нет | см. `docs/hardware-profile.json`; `Ts0P`/`Ts1P` измерены и отклонены — в `traces/stock-load.csv` квантуются в три соседних значения (`Ts0P`: 31.996/32.996/33.996, `Ts1P`: 28.996/29.996/30.996) и не реагируют на нагрузку, берутся ключи низа `Ts0S`/`Ts1S`/`Ts2S` |
| `power` | CPU пакет (SMC) + Radeon (`ioreg Total Power(W)`, запасной — SMC) | нет | см. `docs/hardware-profile.json` |

Таблица выше — назначение каналов; конкретные измеренные ключи для этой машины (и их порядок) — только в `docs/hardware-profile.json`, он источник истины для кода и для `--simulate`.

Показание температуры вне 0–115°C или NaN считается отсутствующим. Канал = максимум по его валидным ключам.

- `gpu`: максимум валидных SMC-ключей GPU; если их нет — `ioreg Temperature(C)`; если нет и его — канал отсутствует.
- **Radeon на батарее выключается полностью.** Пока `gpuActive == false`, канал `gpu` не участвует и **не считается потерянным**. Фаза 0 (`docs/spike-results.md`, «Radeon и gpuswitch»): `gpuActive` = SMC-рейл `PG0R > 1.0` Вт (спит ≈0.12–0.14 Вт, разбужен 7–12 Вт). Пока Radeon спит, ключи `TG*` (SMC) продолжают отдавать правдоподобные показания — не замирают и не уходят в NaN, по ним нельзя определить сон, — поля `ioreg` `temperature`/`power`/`activity` приходят пустыми, а `pciPowerState` остаётся `2`, как и при включённом GPU, то есть бесполезен как флаг.
- `power` = CPU пакет + мощность Radeon (если Radeon выключен или мощность не читается — 0). Нет CPU пакета — канал отсутствует.

### 5.2 Фильтры

Экспоненциальное сглаживание с учётом реального интервала между тиками:
- температуры: τ = 2 с — срезает секундные всплески кристалла i9;
- ватты: τ = 10 с — сигнал «нагрузка держится», тепло скоро дойдёт до корпуса.

Первое валидное значение (при старте, после потери канала, после `didWake`) инициализирует фильтр без сглаживания. Константы в коде, не в конфиге.

### 5.3 Кривые

- Кривых три: `hotspot` (по `max(cpu, gpu)`, при равенстве — CPU), `power` и `chassis`; `power` и `chassis` можно выключить (`{"enabled", "points"}` в конфиге), выключенная кривая всё равно проверяется. У каждой 2–8 точек `(x, y)`, между точками линейная интерполяция, левее первой точки — `y` первой, правее последней — `y` последней.
- `y` — проценты диапазона вентилятора: 0% = стоковый минимум (`F?Mn`, прочитанный при первом запуске и сохранённый в `state.json`), 100% = `F?Mx`. Для вентилятора `i`: `rpm = min_i + y/100 × (max_i − min_i)`.
- Валидация: `x` строго возрастает; `y` не убывает; `y ∈ [0, 100]`; для `hotspot` и `chassis` `x ∈ [20, 110]`, для `power` `x ∈ [0, 200]`.

### 5.4 Сведение

`спрос = max(hotspot(max(T_cpu, T_gpu)), power(W) если включена, chassis(T_chassis) если включена)` по доступным каналам. Ведущая кривая и кристалл, питающий `hotspot`, показываются в UI.

### 5.5 Правила безопасности (в коде, не настраиваются)

| Правило | Действие |
|---|---|
| `cpu` или `gpu` ≥ 95°C (сырое значение, без фильтра) | спрос = 100%, сглаживание пропускается, таймер удержания сбрасывается |
| Нет `cpu` 3 тика подряд (1,5 с), или нет `gpu` 3 тика подряд при `gpuActive == true` | вернуть управление macOS, режим `released(sensorLoss)`. Считается именно потеря (три пропуска подряд), а не «значения ещё нет»: после включения Radeon или сброса фильтров у канала есть те же три тика. Пока Radeon спит, канал `gpu` держит счётчик пропусков, но не значение: удержанное значение сбрасывается немедленно, а счётчик пропусков не трогается — сенсор, вернувшийся из сна без показания, не получает ни залежавшегося значения, ни новой отсрочки потери |
| После `released(sensorLoss)`: критичные каналы валидны 10 с | забрать управление обратно |
| Нет `chassis` или `power` | кривая не участвует |
| Итоговые обороты | всегда в диапазоне `[стоковый минимум, F?Mx]` |

### 5.6 Сглаживание выхода

| Параметр | По умолчанию | Диапазон в конфиге |
|---|---|---|
| Скорость вверх | 25 %/с | 1–100 |
| Удержание после пика | 20 с | 0–120 |
| Скорость вниз | 2 %/с | 0,5–50 |
| Мёртвая зона записи | 3 % | 0–10 |

- **Удержание:** «момент роста» — последний тик, на котором спрос был ≥ текущего выхода. Выход может снижаться, только если с этого момента прошло ≥ `hold` секунд.
- **Мёртвая зона:** новые обороты пишутся в SMC, если выход отличается от последнего записанного на ≥ `deadband`, либо выход равен ровно 0% или 100% и отличается от записанного.

### 5.7 Запись в SMC

Интерфейс `FanActuator`: `take()`, `apply(rpm: [Int])`, `release()`, `verify() -> Bool`. Фаза 0 закрыла вопрос выбора: реализован только **`ForcedActuator`**.
- `ForcedActuator`: `take` пишет `F?Md=1` (ключа `FS! ` на этой модели нет — `docs/spike-results.md`); `apply` пишет `F?Tg`; `release` пишет `F?Md=0`.
- `FloorActuator` (писал бы `F?Mn`) не реализован: SMC отклоняет запись `F?Mn` кодом `0x86` на этой модели (§3, `docs/spike-results.md`, тесты A1/A2). Поэтому профиль актуатор не выбирает, а его ключи `fanMode` и `fanTarget` обязательны.

На каждом тике значение читается обратно; при расхождении перезаписывается (лечит сброс SMC после сна).

Захват управления начинается с текущей скорости вентиляторов; если фактические обороты не читаются вообще, захват начинается со 100% — охлаждающая тулза должна ошибаться в громкую сторону, а не ронять вентиляторы на минимум.

### 5.8 Стартовые кривые

Уточнены по прогону стоковой трассы (Задача 15, `docs/spike-results.md`, «Прогон на трассе стока») и по ревью Задачи 15 (fix round 1 + Ruling R19): `chassis` сдвинут вправо по правилу 95-го перцентиля простоя (запас 3°C). `gpu`: первая точка — по Ruling R15 (95-й перцентиль фазы нагрузки + 3°C, чтобы кривая молчала, пока греется только CPU через общую тепловую трубку), форма выше неё — по Ruling R17: старая форма (65→92°C) поднималась в основном ВЫШЕ порога аварийного обхода в 95°C по сырому (нефильтрованному) значению (`Controller.tick`), который срабатывает раньше, чем туда доходит сглаженное по τ=2с значение — верх кривой не успевал отработать. `power` — по Ruling R18/R19: пересчитан от p95 устоявшегося простоя `40≤t<115` (17.35 Вт, запас 5 Вт → первая точка 23). Эта кривая изначально проваливала критерий простоя на окне `t<115`, но, по Ruling R19, окно `t<115` не является чистым простоем: скрипт записи трассы (в репозиторий не вошёл) запускал `swift build` прямо перед записью, поэтому трасса открывается хвостом этой сборки (сырая мощность ~37 Вт на t=0 — реальная, не ложная тревога) — обязательный критерий простоя проверяется на устоявшемся окне `40≤t<115`. Подробности и обе цифры (settled/full) — в `docs/spike-results.md`. `cpu` не менялся.

| Кривая | Точки `(x → y%)` |
|---|---|
| `hotspot` | 60°C → 0, 72 → 30, 82 → 70, 88 → 100 |
| `power` (включена) | 23 Вт → 0, 38 → 30, 58 → 65, 78 → 100 |
| `chassis` (выключена) | 42°C → 0, 46 → 35, 50 → 75, 53 → 100 |

Решение Димы, 18.09: одна кривая по горячему кристаллу вместо отдельных `cpu` и `gpu`; `hotspot` взяла точки прежней `cpu`, прежняя `gpu` (80/86/90/93) ушла.

## 6. Аварийка и жизненный цикл

### 6.1 Процессы

| Процесс | launchd label | Ключи plist |
|---|---|---|
| `fancurved` | `local.fancurve.daemon` | `RunAtLoad`, `KeepAlive` |
| `fancurved --watchdog` | `local.fancurve.watchdog` | `RunAtLoad`, `KeepAlive` |
| `FanCurve.app` | `local.fancurve.app` (LaunchAgent) | `RunAtLoad`, `LimitLoadToSessionType=Aqua`, без `KeepAlive` |

### 6.2 Режимы демона

| Режим | Кто управляет вентиляторами | Как попасть | Как выйти |
|---|---|---|---|
| `starting` | macOS | запуск | проверки пройдены → `active`; нет → `released` |
| `active` | кривые | проверки пройдены | потеря сенсоров, сон, выключение, завершение |
| `released(reason)` | macOS | потеря сенсоров, сон | автоматически, когда причина ушла |
| `disabled` | macOS | кнопка «Отдать управление macOS» | кнопка «Вернуть кривую» |
| `safe(reason)` | macOS | защита от падений по кругу, неверная модель, нет ключей, запись в SMC не прошла 3 раза подряд | кнопка «Попробовать снова» |

`disabled` сохраняется в конфиге и переживает перезагрузку. Сон переводит в `released(sleep)` только из `active` и `released(sensorLoss)`; `disabled` и `safe` сон не меняет. Сенсоры читаются, пульс и история пишутся во всех режимах.

### 6.3 Запуск демона

1. Запустить цикл тиков (пульс, чтение сенсоров, история) и сокет-сервер. Они работают во всех режимах, включая `safe`, чтобы менюбар видел причину.
2. Проверить `hw.model == MacBookPro16,1`, иначе `safe(unsupportedModel)`; SMC не трогать.
3. `release()` — до проверки ключей: сбой чтения ключа не должен оставить форс упавшего предшественника.
4. Открыть SMC, проверить ключи вентиляторов и карты сенсоров, иначе `safe(missingKeys)`.
5. Если в `state.json` нет стоковых `F?Mn`/`F?Mx` — прочитать и сохранить (первый запуск). Профиль (`docs/hardware-profile.json`) только задаёт стартовые диапазоны вентиляторов; в рантайме источник истины — `state.json` (§7.2).
6. Записать время старта; ≥ 5 стартов за последние 60 с → `safe(crashLoop)`.
7. `enabled == false` → `disabled`. Иначе ждать валидных критичных каналов до 3 с → `active`; не дождались → `released(sensorLoss)`.

### 6.4 Сторож

- Каждую секунду проверяет время изменения `/var/run/fancurve/heartbeat`. Демон обновляет файл на **каждом** тике в любом режиме, кроме одного случая: пока демон не смог вернуть управление (см. последний пункт), пульс не обновляется — пусть сторож тоже попробует.
- Пульс старше 5 с → вызвать `release()` той же реализации актуатора. Операция идемпотентна.
- 15 с после пробуждения из сна проверка не выполняется: после сна пульс устаревает законно.
- В SMC сторож пишет только команду возврата управления.
- Если демон сам не смог вернуть управление (две неудачные попытки подряд), он повторяет возврат на каждом тике и до успеха не обновляет пульс — сторож своим подключением к SMC тоже пытается вернуть управление.

### 6.5 Сон и завершение

- Перед сном (`IORegisterForSystemPower`, `kIOMessageSystemWillSleep`) → `release()`, режим `released(sleep)`.
- После пробуждения: фильтры сбрасываются, пауза 5 с, проверка сенсоров, `active`.
- `SIGTERM` / `SIGINT` → `release()`, выход с кодом 0.

### 6.6 Нижний уровень защиты

Независимо от кода FanCurve i9 сам сбрасывает частоту на 100°C и аварийно выключается при критическом перегреве. Худший случай «оба процесса мертвы при форсе на низких оборотах»: ноутбук горячий и сильно тормозит, но не повреждается.

## 7. Данные и IPC

### 7.1 Сокет

- Путь `/var/run/fancurve.sock`, владелец `root:admin`, права `0660`.
- Протокол: одна JSON-строка на запрос и одна на ответ, соединение переиспользуется.
- Запрос `{"id": 1, "cmd": "status", "args": {...}}` → ответ `{"id": 1, "ok": true, "data": {...}}` или `{"id": 1, "ok": false, "error": "текст"}`.

| Команда | Аргументы | Ответ |
|---|---|---|
| `status` | — | `Snapshot` |
| `history` | `seconds` (1–3600) | массив `Sample` |
| `getConfig` | — | `Config` |
| `setConfig` | `config` | валидированный `Config` или ошибка валидации |
| `setEnabled` | `enabled` | `Snapshot` |
| `setGPUPolicy` | `enabled` | `GPUPolicyState` |
| `retry` | — | `Snapshot` (выход из `safe`) |

`retry` работает только в безопасном режиме: вне него ничего не делает.

`Snapshot`: время, режим и причина, сырые и отфильтрованные значения каналов, спрос по каждой кривой, кристалл, питающий `hotspot`, ведущая кривая (всё в `demand`), последняя ошибка записи SMC (`smcError`), по каждому вентилятору фактические/целевые/мин/макс обороты, состояние автографики.

`Sample` (раз в секунду): время, `cpu`, `gpu`, `chassis`, `power`, спрос %, ведущая кривая (`hotspot`/`power`/`chassis`), обороты обоих вентиляторов, режим.

### 7.2 Файлы

| Файл | Владелец/права | Содержимое |
|---|---|---|
| `/Library/Application Support/FanCurve/config.json` | `root`, `0644` | `version` (= 2), `enabled`, `curves` (`hotspot`, `power`, `chassis`), `smoothing`, `gpuPolicy.enabled` |
| `/Library/Application Support/FanCurve/state.json` | `root`, `0600` | стоковые `F?Mn`/`F?Mx`, исходные `gpuswitch` для AC и батареи, времена последних стартов |
| `/var/run/fancurve/heartbeat` | `root`, `0644` | пустой файл, важен только mtime |

Конфиг пишет только демон, после валидации, атомарно (временный файл + `rename`). Битый конфиг на диске при старте → переименовать в `config.json.bad`, работать на стартовых значениях, показать ошибку в `Snapshot`.

### 7.3 История

Кольцевой буфер в памяти демона: 3600 записей по одной в секунду. На диск не пишется: переживает перезапуск приложения, но не демона.

### 7.4 Логи

`os_log`, subsystem `local.fancurve`. Пишутся только смены режима, ошибки SMC, ошибки конфига. Каждый тик не логируется.

## 9. Автографика

- Включение: если в `state.json` нет исходных значений — прочитать `pmset -g custom` и сохранить `gpuswitch` для AC и батареи в `state.json` до первой записи `pmset`; если сохранить не удалось, автографика не включается. Затем `pmset -c gpuswitch 1` и `pmset -b gpuswitch 2`.
- Выключение: записать сохранённые исходные значения и стереть их из `state.json`: следующее включение прочитает их заново.
- Переключение при подключении кабеля делает сам macOS; демон в этом не участвует.
- Состояние (`включено`, фактические значения AC/батарея) читается разбором `pmset -g custom` и показывается в попапе. Если Системные настройки перезапишут значения, это будет видно, но демон с ними не спорит.
- Известные последствия: на зарядке Radeon постоянно добавляет ~7–8 Вт тепла; после отключения кабеля macOS вернётся на встроенную графику только когда Radeon отпустят все приложения.

## 10. Установка и удаление

- **Сборка:** `swift build -c release` (как пользователь, не root; сборка от root оставляет root-owned файлы в `.build`).
- `scripts/build-app.sh` (План 3): `swift build -c release` (всё, включая демон), сборка `dist/FanCurve.app` (`packaging/Info.plist`, бинарник `FanCurve`, иконка `packaging/AppIcon.icns`), `codesign -s -`. Установка целиком: `./scripts/build-app.sh && sudo ./scripts/install.sh`.
- Иконка приложения (решение Димы от 29.09): крыльчатка турбины с фото и вокруг неё шкала тахометра со стрелкой-точкой высоко и красной зоной в конце — обороты растут. Исходник `docs/icon/app-icon.svg`; для 16 и 32 px упрощённый `app-icon-small.svg` (20 лопаток потолще, шкала без делений). `scripts/build-icon.sh` рендерит их в `packaging/AppIcon.icns` (нужен librsvg из brew); `.icns` лежит в репозитории, поэтому сборке приложения librsvg не нужен.
- `scripts/install.sh` (через `sudo`):
  1. `fancurved` и `fancurvectl` → `/Library/PrivilegedHelperTools/local.fancurve/`, владелец `root:wheel`, `0755`. Путь, принадлежащий root, чтобы обычный процесс не мог подменить бинарники, которые запускаются от root.
  2. Создаёт symlink `/usr/local/bin/fancurvectl` → `/Library/PrivilegedHelperTools/local.fancurve/fancurvectl`.
  3. Два plist (`local.fancurve.daemon.plist`, `local.fancurve.watchdog.plist`) → `/Library/LaunchDaemons/`, `launchctl bootstrap system`.
  4. (План 3) `FanCurve.app` → `/Applications/`.
  5. (План 3) LaunchAgent → `~/Library/LaunchAgents/local.fancurve.app.plist` пользователя, запустившего `sudo` (`SUDO_USER`; plist принадлежит ему), `launchctl bootstrap gui/<uid>`; без сессии рабочего стола приложение стартует при следующем входе. При обновлении агент снимается первым, запущенная копия приложения закрывается.
  6. Повторный запуск = обновление (bootout → замена файлов → bootstrap).
- **Логи:** ошибки запуска демона падают в `/var/log/fancurve.log` и `/var/log/fancurve-watchdog.log` (stderr каждого LaunchDaemon, задано в plist). Регулярные логи (смены режима, ошибки SMC, ошибки конфига) — через `os_log`, subsystem `local.fancurve` (читать `log show --last 2m --predicate 'subsystem == "local.fancurve"'`).
- `scripts/uninstall.sh`: (План 3) сначала снять LaunchAgent и закрыть менюбар — чтобы приложение не показало остановку демона как сбой → bootout демона и сторожа (демон по `SIGTERM` сам возвращает управление) → `fancurved --restore` (ещё раз вернуть управление вентиляторами и восстановить исходные `gpuswitch` из `state.json`, работает даже если демон мёртв) → удаление всех файлов. Домашняя папка пользователя берётся из `dscl`; если её нет, файл агента не трогается.

## 11. Тестирование

**Модульные тесты (Swift Testing, `swift test`):**
- `FanCurveCore`: уровень значка-крыльчатки (пороги, границы 5% и 100%, гистерезис 2%); интерполяция (края, точки, между); валидация кривых и конфига; фильтр (отклик на скачок: 63% за τ, неравные интервалы); сведение и ведущая кривая; правила безопасности (95°C, потеря и восстановление критичных каналов); сглаживание (скорость вверх, удержание, скорость вниз, мёртвая зона); перевод % → RPM с ограничением; автомат режимов; защита от падений по кругу; JSON конфига и протокола туда-обратно; кольцевой буфер.
- `FanCurveHardware`: кодеки на известных векторах — `flt` `0088a545` = 5297.0 и `00489945` = 4905.0 (логи MFC), `fpe2` 3500 = `36b0`, `sp78`, `ui8/16/32`, FourCC ключей.

**Прогон трасс:** `fancurved --simulate traces/<file>.csv` прогоняет записанную трассу через `FanCurveCore` без SMC и выводит CSV решений. Трассы из Фазы 0 лежат в репозитории.

Формат трассы (пишет `smc-probe record`): CSV с заголовком; первая колонка `t` — секунды от начала записи; остальные колонки названы именем SMC-ключа (`TCXC`, `F0Ac`, …) или `ioreg.gpu.temp`, `ioreg.gpu.power`; пустая ячейка — нет значения. Какие колонки образуют какой канал, задаёт карта каналов из `docs/spike-results.md`; при прогоне она передаётся в `--simulate`.

**Приёмка на железе** (вручную, вместе с Димой):
1. `smc-probe dump` работает без root.
2. После установки менюбар показывает крыльчатку с температурой горячего кристалла, в попапе — все четыре канала и режим `active`; кнопки попапа и редактор кривой работают против живого демона.
3. Нагрузка (сборка или 16 × `yes > /dev/null`, 5 мин): вентиляторы раскручиваются раньше, чем в стоке; сравнение с трассой стока из Фазы 0 по максимальной температуре CPU и корпуса.
4. `kill -9` демона → launchd перезапускает. `kill -STOP` демона → сторож возвращает управление macOS не позже чем через 6 с (чтение `F?Md`); `launchctl bootout` демона → демон возвращает управление сам по `SIGTERM`.
5. Сон и пробуждение: управление отдаётся перед сном, возвращается после.
6. Автографика: на зарядке Radeon, на батарее автовыбор; выключение тумблера возвращает `2/2`.
7. Перезагрузка: демон активен до входа, менюбар появляется после входа.
8. `uninstall.sh` возвращает стоковое состояние.
